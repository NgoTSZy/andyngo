§0 问题（ISS-113）
--------------------------------------------------------------------------------
`pre + sep` 这个值被用在**两个**地方：① 构造**扫描已有号**的模式（`^pre+sep+数字`）② 构造**新号**。
它的正确性**没有任何东西检查**。sep 传错 → 扫描模式与文件里既有的号**对不上** → 一条都扫不到
→ 计数器从 1 开始。实测（上一轮，我自己踩的）：
```

WARN 写入成功，但该文件有**未登记**的重复号: ISS-001×2（按 DEC-026 追加勘误）
ALLOC ISS 001
```
→ 一行 `ISS 001 open …` 落盘。撞号检查**响了**，但**是 WARN、写已经发生**（记录层 append-only）。

§2 改动（401 → **499** 行 · `6178ba3f…` → `d9427ddc4144583b07819e498ae27331`）
--------------------------------------------------------------------------------
```
function esc(x) { return x.replace(/[.*+?^${}()|[\]\\]/g, '\\$&'); }   // 从下面提上来，两处共用

function prefixForms(src, pre, sep) {
  const any = new RegExp('^' + esc(pre) + '[\\s-]', 'gm');              // 任意分隔符形态
  const hit = new RegExp('^' + esc(pre) + esc(sep) + '\\d', 'gm');      // 本次要用的那一种
  return { anyForm: (src.match(any) || []).length, matched: (src.match(hit) || []).length };
}
```
守卫（**放在取锁之前** —— 拒跑必须是「根本没写」）：
```
if (pf.anyForm > 0 && pf.matched === 0) { …四行说明… process.exit(4); }
```
**为什么不是「扫到 0 就拒」**：真正的新文件扫到 0 是**正常**的（第一次写 `EVT 001` 就是这个形状）。
要区分的是「**文件非空但扫不到**」—— 那只有两种解释：**分隔符传错** 或 **号段形态变了**，两种都该停下。

§5 ★ 第一次反向验证是「空断言」（**ISS-034 的形状**）
--------------------------------------------------------------------------------
第一版反向验证用的正文是 `iss113-body.txt` —— 而**那份正文已经在 `issues.md` 里**。
于是 `alloc.sh` 的**幂等查重先命中**（`SKIP 正文已在该文件里（本命令被执行过两次）→ 不重复追加`，
rc=0），**根本没走到守卫**。而输出看起来像「**没写入 = 守卫生效**」——
**两件事都没发生，被当成结论一致**（ISS-034 的原形）。
换成内容**不在**文件里的正文（`iss113-probe.txt`，带唯一标记 `probe-iss113-a1b2c3`）才测到真东西。
**教训**：验证「某条守卫拦住了 X」时，**必须先证明「X 真的到达了守卫」** —— 否则验证的是**上一层**。
