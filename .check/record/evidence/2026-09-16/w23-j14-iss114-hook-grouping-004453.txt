## §1 ② 为什么不成立（决定性实测）

`RE_SPAWN` 的**真形状**要求：`[HookExecutor] spawn` + `cmd=`。而我自己 grep 日志时写的命令行是：

```
grep -c 'HookExecutor. spawn' …
```

—— **`. `（点加空格）而不是 `[`**，**无方括号** → **匹配不上** `RE_SPAWN`。所以**我的测量行为不会抬高 `[99]` 的数**。

**实测（窗口 2026-09-16 · 顶层 `.log` 文件 10 个）**：

```
spawnTotal = 836        （含 cmd= 的 spawn 行）
mine       = 775        （其中含 .check/ 的）
---- mine 里按 cmd 的最后一个脚本名分组 ----
immunity-hook.js            775     ← 全部
（取不到脚本名的）             0     ← 噪声 0
```

**`mine` 里取不到脚本名的 = 0** —— 也就是说**自指/噪声候选一条都没有**。

**当年那个「40 行自指」是另一种数法的产物**：数「含 `.check/` 的行」，**不要求 spawn 形状**。
那不是 `[99]` 的口径。**它记的是测量方法的缺陷，不是判据的缺陷** —— 这一条纠正记在 CHG-191。

## §2 ① 为什么仍是潜在的（当前无实际误判）

宿主读的那份 `~/.workbuddy-ai/settings.json` **只登记了一个 hook**：

```
PostToolUse → .check/immunity-hook.js
```

所以现在**不存在**「两个 `.check/` hook 混在一个计数里」的情形 → **没有实际误判**。

窗口里另有别的脚本名，但**都不指向 `.check/`**（来自**插件**，不进 `mine`）：

```
setup.sh                      54
save-on-subagent-stop.mjs      7
```

**触发条件**：**有人登记第二个指向 `.check/` 的 hook** —— 那时 `mine` 会把两者混在一起，
**任一个在跑门禁就绿**，另一个静默死掉**看不见**。这正是 ISS-103 挖出那条事实的同族形状。

## §4 为什么不直接加门禁（**这是本条仍未结的唯一原因**）

判红需要一份「**应当**被 spawn 的名单」。而：

1. `hook-session-start.js` 已由 **DEC-041** 裁决「**不再要求被加载**」→ 名单必须能表达
   「**已知未加载 + 理由**」（同 X1 的 `.check/record/exit-codes.md` 登记表形态）；
2. 那是**改门禁语义** —— **乙类**，不在无人裁决时擅自加；
3. 且判红会引入**新的假红面**：有的 hook 类型**本来就不在一个窗口内触发**，
   拿「**窗口内 0 次**」当红，**正是刚在 ISS-116 里修掉的那种错**。
