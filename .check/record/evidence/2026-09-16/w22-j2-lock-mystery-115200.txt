W22 J2 · 追查「锁自行消失」：找到一个真缺陷、一个更坏的东西、以及一个**每次都在发生的重复执行**
留证时间：2026-09-16T03:52Z（本地 11:52）
作业：收尾时 `write-lock.js status` 报「本来就没有锁」，而 17 分钟前 `acquire` 明确成功 —— 查它去哪了

§0 一句话
**锁的消失没能归因**（不猜）。但顺着查下去抓到三件事：
① `write-lock-test.sh` **与生产共用锁文件、开头无条件 `rm -f`** → 跑一次自测就删掉别人的锁，
   而 automation §0.3 取锁、§一.6 跑自测 → **每轮都自毁**（**已确证，已修**）；
② `file-history.js --get` **静默取错块**（已修，见 ISS-059）；
③ **每条带 bypass 提示的命令实际被执行了两次** —— 这是本段最重要的发现。

§1 锁消失的时间线与已穷尽的机制（DEC-029）

```
03:13:23Z  acquire session:interactive-w22 20   → LOCK acquire（成功）
03:13:23Z  status（同一命令内）                  → LOCK held … since=2026-09-16T03:13:23Z pid=3684
03:13–03:29  只做过：md5sum / grep / 编辑两个记忆文件 / 读验收输出
约 03:30Z  [ -f .check/.write-lock ] → 假 · status → LOCK free · release → 「本来就没有锁」
```
已穷尽：(a) 全仓库 `grep -rn '\.write-lock'`（排除 `file-history/`）→ 除锁自己的 `release`/`takeover` 外，
**唯一删除路径是 `write-lock-test.sh:27`**；(b) 宿主 `[safe-delete]` 日志 → **11 条命中全部在 11:05–11:06 本地（03:05–03:06Z）**，
**全部早于取锁**，之后无任何删除记录；(c) 沙箱日志两处命中经查是**我自己的 grep 被扫描**；
(d) **持久性本身正常**（`acquire probe:persist` 后**下一条独立命令**仍读到 `age=5s`）。
**结论：删除者未确定。** 不归因给 (a) —— 时间戳对不上。

§2 ★ 真缺陷：守卫把被守卫的东西删了（ISS-060，已修）

`.check/tests/write-lock-test.sh:27` 原文：
```bash
# 起手清干净（上一轮异常退出可能留锁）
rm -f .check/.write-lock .check/.write-lock.takeover
```
**它和生产共用同一个锁文件路径。** 于是：
- 跑一次自测 = **静默销毁别人正持有的锁**，输出一切正常，第 16 项「跑完无残留」还报 PASS；
- **常态比偶发更坏**：automation §0.3 `acquire` → §一.6 跑自测 → **每轮把自己的锁删掉**，
  之后全部「改源文件」都在**无锁**状态下发生，而**每一步都报成功**。

修法：起手先 `status`，**有人持有就拒跑**（`rc=2`，同 DEC-013）；只有「存在但已过期」才允许清。
**不引入任何跳过守卫的开关**（DEC-023）。并加**自指守门人**（第 17/18 项）：
取一把 `guard:regression` 锁 → **再跑一次本脚本** → 断言 `rc=2` 且锁文件**逐字节不变**。
递归只有一层（内层一进来就撞守卫、在动任何文件**之前**退出）。

实测：空闲 **18/18 · rc=0**；持锁 **拒跑 rc=2**，锁内容 `demo:holder 2026-09-16T03:32:05Z 21416 10`
**前后逐字节相同**。

§3 ★★ 更坏的东西：**每条带 bypass 提示的命令实际执行了两次**

现象：`newid.js` 连续报 `ALLOC-FAIL 锁超时（5s），未写入` + `rc=3`，
而**文件里确实多了一行**；并留下 **0 字节的 `issues.md.lock`**。

对上的模型（逐条证据，不是推测）：

| 观测 | 用「命令执行两次」解释 |
|---|---|
| `@iss060` / `@iss061` 两条 → 两次 `rc=3`，文件里多 **两行**、**正文都是 iss060** | 第 1 次执行（沙箱内）写 060；第 2 次执行写 061（正文同一个文件）；而**看到的 rc=3 来自第 3、4 次尝试** |
| `@iss062` / `@iss063` → 两次 `rc=3`，只多 **ISS-062** | 第 1 次执行写了 062 并**留下锁**；第 2 次撞锁 → `rc=3` |
| `@iss064b` → `ALLOC ISS-065`，而 **064 与 065 逐字相同** | 第 1 次写 064；第 2 次写 065（正文同一文件）→ **同一条命令两行** |
| `acquire demo:holder 10` 报 `LOCK busy … age=254s since=03:32:05Z` | 第 1 次执行在 03:32:05Z 建锁；**批准等待 254 秒**后第 2 次执行撞上它 |
| 每条命令都带 `⚠️ Sandbox bypassed (escalation-approved)` | 即「**先被沙箱拦下 → 等用户批准 → 以 bypass 重跑**」 |

**每一条观测都对上，没有一条需要额外假设。** 所以：
**带 bypass 提示的命令 = 被执行两次；第一次的输出不显示，但它的写入/副作用是真的。**

**为什么这件事最重要**：本仓库的核心动作是**追加记录**（EVT/ISS/DEC/CHG）。
如果命令会执行两次，那么**每一条记录都可能被写两遍**，而**判据看不见**
（I1–I7 只查字段数/seq/路径/ts/双向单射/status —— 两行内容相同、编号连续，全部合规）。
这与本项目反复踩的形状同族，但这次**不是我们的代码写错了，是执行环境**：
**「我以为它跑了一次」是一个从未被验证过的前提。**

§4 它还可能解释什么（**未证实，不作为结论**）

ISS-062 那条「锁自行消失」：若被沙箱拦下的那一次执行**会被回滚**，
则「先建锁（沙箱内）→ 被拦 → 回滚 → 重跑」可以解释锁的消失。
**但这需要沙箱日志里有回滚记录，而实测没有**（`grep -h 'deny\|block\|rollback' logs/sandbox/20260916/*.log` → 0 命中）。
所以：**仍归为未确定。**

§5 当前处置与下次要抓的现场

- **临时处置**：每次 `newid.js` 分配前 `rm -f .check/record/*.lock`（本轮就是这么做的），
  分配后**核对「号 → 正文」是否对得上**（本轮抓出了 3 处错位/重复，见 ISS-066 的映射表）。
- **不要改 `newid.js`**：本轮已确认「写两次」来自**执行环境**，不是它；
  改它等于给一个错误的假设打补丁。
- **下次要抓的现场**：① 出现 bypass 提示时，立刻 `ls -la` 目标文件并**对比 bypass 前后**；
  ② 查沙箱**中心**日志里的 escalation 记录（不是 `logs/sandbox/`）；
  ③ 每条追加命令后立刻数一次行数。
- **建议的长期规则**（**未实施**）：**任何带 bypass 提示的命令，其副作用一律按「可能已发生两次」处理**；
  追加类命令必须**幂等或可检测**（例如写完立刻复核「最后两行是否相同」）。

§9 三句

1. **守卫把被守卫的东西删了** —— 而它自己的残留检查还报 PASS。
   **一条只检查「跑完有没有残留」的断言，永远不会发现「它删掉了别人正在用的东西」。**
2. **「我以为它跑了一次」是一个从未被验证过的前提。** 本轮所有怪现象
   （报 rc=3 却写入了、号与正文错位、同一条命令两行、锁消失）
   在「命令执行两次」这一个假设下**全部对上，且不需要额外假设** ——
   而发现它的入口，只是收尾时多看了一眼 `status`。
3. **不要给错误的假设打补丁。** 一度想改 `newid.js` 加「陈旧锁清理」，
   但证据指向执行环境而非它 —— **在根因未定之前改代码，只是把不确定性埋进代码里。**
