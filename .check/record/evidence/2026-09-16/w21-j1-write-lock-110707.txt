W21 J1 · 写权锁：把「两个写者 + 一条钝规则」换成「能写、但不同时写」
留证时间：2026-09-16T03:07Z（本地 11:07）
作业：核实 DEC-025 与 automation 提示词是否一致；若不一致，给最小机制

§0 一句话
记录层 `DEC-025`（「**本自动化**只做只读回归，**不改任何源文件**」）与 automation 提示词 §三
（「**能修的就修**」）**直接矛盾**，且**没有任何判据比对这两层**。
真问题不是「该不该让 automation 写」，而是「**两个写者不能同时写**」
→ 建了一把工作区级写权锁（O_EXCL 取锁 + 原子抢占 + **持有者声明 TTL**）。

§1 缺陷（ISS-057）
两处规则互相矛盾且无判据：
  · 记录层 `DEC-025`（2026-09-16T01:16Z，**automation 自己写的**）：
    「本自动化只做只读回归，不改任何源文件；未结项只做『事实复核 + 追加勘误』」
  · automation 提示词 §三：「**能修的就修**；不能修的必须在报告里写清为什么不能修」
**实测后果**：今天 automation **按 DEC-025 执行**（W16 报告写明「**零源文件改动**」），
于是提示词里那句「能修的就修」**永不兑现** —— 而交互会话通常一直开着，
按「有并发写者就退让」执行等于**永远退让**。
**为什么没人发现**：记录层与提示词是两层，**没有任何判据读它们的关系**
（同 ISS-050 家族：判据的输入没有判据；也同 ISS-051 家族：结构性的**必然否定**）。

§2 但 DEC-025 的顾虑是真的（所以不是删它，是换实现）
并行 Edit 会互相覆盖且**两次都报成功**（本项目踩过 3 次）；两个写者同时改同一文件会**静默丢更新**。
所以正确的动作不是「退让」，而是「**排队**」。

§3 机制
新增 `.check/write-lock.js`（152 行）：
  ① 取锁用 `open(..., 'wx')`（O_EXCL）—— **原子创建**，不是「先查再建」那种两段式（同 DEC-027）。
  ② **抢占也原子**：过期锁的抢占先拿 `.write-lock.takeover` 标记（同样 O_EXCL），再换锁 ——
     否则两个进程可能同时判定「过期」并同时重建。
  ③ **只放自己那把**：`release` 校验 holder，不是自己的就拒跑（否则会替别人解锁）。
  退出码三态（同 DEC-013）：`0` 拿到/放掉 · `2` **拒跑（没有写入）** · `4` 参数错。
  锁文件 `.check/.write-lock`，内容 `<who> <iso> <pid> <ttlMin>`；**不进记录层**（运行期状态，不是历史）。

§4 ★ 第一版有一个真缺陷，而且是**跑出来的**，不是审出来的
第一版把「过期」按**调用方**给的 TTL 判。实测：A 声明 60ms，2 秒后 B 拿 30 分钟 TTL 去取 →
`LOCK busy holder=session:staleA age=2s ttl=30min`，**永不抢占**。
即：**一个谁都能给自己发长期通行证的判据，等于没有判据**（同 DEC-023 家族）。
**修法**：TTL 由**持有者声明并写进锁文件**（第 4 字段），**所有人按持有者声明的 TTL 判过期**；
调用方给的 `ttlMin` **只**用于它自己取得锁时的那份声明。
**修后实测**：`LOCK takeover automation:staleB 抢下的过期持有者=session:staleA（年龄 2s，声明 1s）`。

§5 实测
`bash .check/tests/write-lock-test.sh` —— **16/16 全通过**：
```
1 status 空闲 → 0          2 acquire A → 0            3 acquire B 被占 → 2（拒跑）
4 release B 不是自己那把 → 2  5 status 读到持有者 → 0    6 release A → 0
7 status 又空闲 → 0         8 acquire A 声明 60ms → 0  9 acquire B 抢过期锁 → 0（takeover）
10 release B → 0           11 缺参数 → 4              12 非法 ttl → 4
13 取得锁时打印自己的声明     14 status 显示持有者声明的 TTL   15 释放后回到 free   16 跑完无残留
```
（量退出码**不经管道** —— 管道拿到的是 `tail` 的状态，恒 0，本项目踩过。）

     §三 归档那一步加 `file-history.js` 的指针（ISS-056 的落地）· §四 加第 7 步（收尾放锁）·

  ③ **常驻层 `~/.workbuddy-ai/MEMORY.md`**：加一条写权锁规则 ——
     **否则只有 automation 守规矩，交互会话照样会撞**。**机制必须对「所有写者」生效，否则不是机制。**

§7 残留与未验（**不假装已覆盖**）
- **锁只在「写者自愿取锁」时有效** —— 它防不住一个不取锁的写者。目前取锁方 = automation 提示词 + 常驻记忆。
  **「所有写者都取锁」没有判据**（无法机械判定一次 Edit 是否发生在锁内）。
- **TTL 是「用时间代替活性检测」**：持有者活着但跑超自己声明的 TTL，锁会被抢走。
- **抢占路径没有并发压力测试**：只测了单进程的 takeover；**两进程同时抢没有真跑过**。
- 锁自测**已接进 automation §一**，但**没有接进 `acceptance.js`** ——
  验收不会因为锁坏了而报红（刻意：验收不碰运行期状态）。**代价是：锁坏了只有 automation 那一轮会发现。**

§9 三句
1. **两条规则互相矛盾、而没有任何判据比对它们，比任意一条错更坏** —— 因为两条都在「被遵守」，
   结果是**谁也不知道系统实际按哪条跑**。
2. **钝规则的失效方向是「静默退让」** —— DEC-025 不报错、不亮红灯，它只是让「能修的就修」永不发生。
   **一条让系统什么都不做的规则，在验收表上长得和「今天没事」一模一样。**
3. **锁的第一版第一次跑就有缺陷**（过期按调用方 TTL 判）—— 又一次印证：**机制必须跑，而不是审。**
